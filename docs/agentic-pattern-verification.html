How to read this

What a gate is

Each gate states what it proves, gives the exact command, shows the output that counts as a pass, and names the failure it exists to catch. A gate that only proves “the code runs” is not worth a gate; every one below is here because something specific went wrong once, or could.

Statuses mean exactly three things. Verified — run on this branch, output reproduced below. Operator — needs Docker or a funded API key; not run. Blocked — run, and it currently fails.

06

The generated project’s own lint

Verified

Proves That a freshly generated project passes the CI it ships with. Its workflow runs uv run ruff check ., so this is the first thing that happens to a user who generates a project and pushes it.

shell · generated project root
uv run ruff check .

All checks passed!
What this used to fail with, and why

Until 7 August this reported Found 15 errors under ruff 0.16.1. The errors were real but they were a symptom: the generated [tool.ruff] set target-version, line-length and src but never selected any rules, so the enabled set was whatever the installed ruff defaulted to — --show-settings reported 414 rules enabled under 0.16.1, against roughly 60 for the classic E4/E7/E9/F. With ruff>=0.6 floating and no lockfile, a project nobody had touched could go red because a newer ruff resolved.

Fixed by selecting rules explicitly in both pyproject.toml files — the second of the two options this gate originally proposed. Pin the rules, not the tool: bounding ruff<0.17 would freeze users on today’s linter to work around a config gap, and would need bumping forever.

Why the suite never caught it

tests/conftest.py lints bakes with uvx ruff@0.15.20 while a generated project resolves ruff>=0.6 to 0.16.1 — so test_full_bake_all_patterns_lints_clean was linting with a different ruff than any user gets, and stayed green for the whole stretch where every bake was failing. The pin now tracks what users resolve.

Worth recognising the shape: a cheap tier substituting its own stable answer for exactly the variable that breaks in production. The same shape hid the missing list_repo_files tool (cassettes hard-code the file path that live path-discovery could not derive) and a grader schema that was a 400 on arrival (MagicMock stands in for the API, so its validator never saw the schema). Three instances in one week.

PassClean across four cookiecutter answer combinations — defaults, no-agentic, no-lakehouse, and minimal — because two of the corrected import blocks are Jinja-conditional and only some answers render them.

Compose resolves a writable uid, with or without .env

Verified

Proves That a fresh clone works. .env is gitignored, so it is absent on any machine that did not run cookiecutter. The airflow-init service runs as root and chowns the bind mounts to whichever uid airflow will use, so the demo does not depend on that file existing. Both services must resolve the same uid — if they diverge, init hands the mounts to a uid that is not the one writing.

A caveat worth stating

This failure is Linux-only. Docker Desktop on macOS maps bind-mount ownership through its VM, so uid 50000 can already write and the bug cannot be reproduced there. If you are verifying on a Mac, gate 08 checks that the wiring is consistent; only a Linux host proves the mounts are writable.

09

The demo, end to end, in Docker

Operator

Proves The whole loop as a user meets it: a task fails for a real reason, the healer wakes up, and a patch lands on your host filesystem. This is the gate the slow tier approximates but cannot replace, because only this one exercises the actual container, the actual bind mounts, and the Airflow UI.

shell · generated project root · needs Docker
docker compose up -d airflow-standalone

# airflow-init runs first and exits 0; standalone waits for it.
docker compose ps -a

# Open http://localhost:8080 and trigger example_events_dag
# with this run config (any Pattern combination with Batch):
#   {"failure_mode": "schema_drift"}

Then check the four things the run is supposed to produce:

shell · after the DagRun finishes
ls artifacts/*.patch          # a unified diff, ready to git apply
ls artifacts/*.json           # proposed PR title, body, confidence
git apply --check artifacts/*.patch   # the patch actually applies
ls -l logs/                   # owned by you, not by 50000
A bug this gate found: the stack would not start at all

On a macOS host running colima, airflow-init exited 1 with chown: changing ownership of ‘/sources/logs’: Permission denied, and airflow-standalone never started because it depends on init via service_completed_successfully. Init already ran as root, so this was not a missing privilege — root was being refused.

Docker backed by a VM (colima, Docker Desktop, Rancher, OrbStack) shares host directories through a filesystem that denies chown to everyone including root, and does not need it: the share already presents its files as writable to the container user whatever uid it runs as. Confirmed on the failing host, where a container running as 501:0 wrote to the mount happily while root could not chown it. The command chained mkdir && chown, so a refusal that changed nothing was fatal.

The chown is now best-effort and a writability probe decides. The probe runs under setpriv --reuid as the uid airflow will actually use, never as root — a root probe passes on precisely the unwritable mount it exists to catch, trading a loud false failure for a silent false pass. Both outcomes were checked on a real filesystem rather than on the VM share, whose permissions are virtualised away: a root-owned 755 directory probed as uid 12345 exits 1 with the FATAL message, and the same directory after a successful chown exits 0.

Verified on this host — up to the trigger

airflow-init exits 0 with a note that chown was declined; the stack comes up; curl localhost:8080 returns HTTP 200; example_events_dag registers from example_dag.py with no import errors; and the container’s logs appear on the host owned by 501:20 rather than 50000, which is what the mount is for.

The DagRun itself is still yours to make: the healing task calls the API and needs a key. That is the only reason this gate is not marked Verified.

Passload ends failed, heal_on_failure ends success, exactly one .patch and one .json appear, and the patch applies cleanly. Nothing is applied for you — the agent proposes, you merge.

The live agent

Operator

Proves That the real tool loop works against the real API — tool specs accepted, multi-turn dispatch, and a diagnosis the model actually produced rather than one replayed from a cassette. Costs money and is non-deterministic, which is exactly why it does not gate CI.

shell · generated project root · needs ANTHROPIC_API_KEY
export ANTHROPIC_API_KEY=sk-ant-...
uv run pytest -m live -q

Watch for Without the key these skip rather than fail. A run of “0 selected” means the marker is missing, not that everything passed.

This gate has already earned its keep

It is the gate that caught the agent having no way to find a file. A FailureContext names a dag_id and a task_id, never a path, and the DAG id example_events_dag does not match the filename example_dag.py — so the agent burned all twelve iterations on seventeen failed read_repo_file guesses, degenerating to casing permutations, then correctly refused to speculate and set confidence low. Both required criteria failed from that single cause.

Replay could never have caught it: the cassettes hard-code the correct path, so ReplayRunner hands the agent the answer to the exact question the live agent fails at. A list_repo_files tool closed it.

PassThe live tests pass, and the diagnosis names the real offending field rather than something generic. Not re-run under -m live since the fix, though gate 11 drives the identical loop through ClaudeRunner and produced a correct high-confidence patch on every case.
11

Graded evals

Verified

Proves Agent quality, not just plumbing: an LLM grader scores a live run against the per-criterion expectations declared in evals/cases/*.yaml and writes a report you can read.

shell · generated project root · needs ANTHROPIC_API_KEY
uv run pytest -m graded -q
ls evals/reports/             # timestamped .md and .json per run
Two bugs this gate found, both in the grader

First run: BadRequestError — for ‘integer’ type, properties maximum, minimum are not supported. Structured outputs accept only a subset of JSON Schema, and numerical constraints are rejected, so the grade schema was a 400 before the model was ever consulted. Score bounds are now an enum of [0…5], which is a supported keyword and the same constraint.

Second run: grader skipped required criteria. It had skipped nothing — it graded all six criteria and scored the agent 5/5 — but criterion was a free-form string, so it wrote labels rather than identifiers, and no two runs agreed: tools_called came back as 'tools_called must_call' on one case and 'tools_called: must_call all of [read_task_log, read_repo_file, propose_patch]' on the other. The schema is now built per case, with criterion an enum of that case’s own rubric keys.

Both fixes are the same move: make the wrong answer unrepresentable rather than ask for the right one. Both are now guarded by tests that need no API key — one walks every output schema for keywords the subset rejects, the other asserts every criterion named in a case’s score is nameable from its expect. Each was verified to fail against the exact defect it describes before being kept.

PassBoth cases meet their required criteria; the agent scored 5/5 on each. Advisory criteria may miss; read the report rather than only the exit code. Run by the operator on 7 August — console output not reproduced here, unlike the gates above, because it was reported rather than captured.

If a gate fails

Fix forward rather than skipping. Every gate here exists because the thing it checks broke once, or is the only place a class of bug is visible. A gate you deselect to get a green run is a gate that was doing its job.
