The Agentic Self-Healing Pattern

When a batch DAG task fails, a bounded agent reads the failure logs and the repository source, diagnoses the root cause, and writes a patch for a human to review. Nothing is applied automatically. The entire run is recorded as one JSON array so it can be queried, scored, and argued with afterwards.

Why

The problem this actually solves

A data pipeline fails at 3am. The exception is in a log; the cause is in a source file; the fix is three characters. The expensive part is not the fix — it is the round trip between noticing, finding the log, reading the schema, and working out which of the two sides is wrong.

This Pattern compresses that round trip into an artifact waiting for you in the morning: a diagnosis, a unified diff, and a full record of how the agent got there. The deliberate limit is that it stops at the artifact. The agent proposes; you merge.

Design stance

Every capability the agent does not have is load-bearing. It cannot run shell commands, cannot write to disk, and cannot reach outside the project root. A bad run costs an unused .patch file, not a corrupted repository.

Architecture

Shape of the system

Six modules under src/<slug>/agentic/, each with one responsibility. Two of them are protocols rather than implementations — those are the seams the whole design rests on.

ModuleLinesResponsibility
contracts.py95Typed records only. No behaviour beyond one serialiser.
tools.py298The four tools and their path confinement. The security boundary.
runner.py280AgentRunner protocol plus the fake and live implementations.
tracing.py230Recording a run and persisting it. Never fails the task.
publisher.py205Turning a result into something reviewable.
dags/healing_dag.py225The only module that imports Airflow.

The two seams

AgentRunner isolates every source of non-determinism. Its signature is run(ctx, recorder) -> AgentResult. Above that line, everything is ordinary Python you can test with plain pytest. Below it sits a live model call.

AgentResult is a single artifact with three consumers: the publisher renders its edits into a diff, the trace sink persists its elements, and the eval suite asserts on all three fields. One producer, three consumers, no back-channels between them.

Why one Airflow import matters

Because only healing_dag.py imports Airflow, the other five modules are unit-testable without a scheduler or a metadata database. That single constraint is what makes 104 tests run offline in seven seconds. It is verified mechanically, not by convention — a grep across the module is part of review.

Runtime

One healing run, end to end

The orchestrator, verbatim

run_healing takes its three collaborators as arguments. That is the whole reason the loop is testable: production passes nothing and gets live implementations; tests pass fakes and get determinism.

src/<slug>/agentic/dags/healing_dag.py
def run_healing(
    ctx: FailureContext,
    runner=None,
    sink=None,
    publisher=None,
) -> tuple[Trace, PublishedPatch]:
    """Diagnose, trace, and publish. Collaborators are injectable for tests."""
    root = Path(ctx.project_root)
    runner = runner or ClaudeRunner()
    # Both defaults are rooted at the project, not at the worker's CWD.
    # LocalPatchPublisher and GitHubPublisher would otherwise disagree about
    # where artifacts live, and the worker's CWD is not a mounted volume, so
    # CWD-relative artifacts never reach the host.
    sink = sink or default_sink(root)
    publisher = publisher or default_publisher(root)

    recorder = TraceRecorder(...)
    tool_ctx = ToolContext(project_root=root, log_path=Path(ctx.log_path))

    try:
        result = runner.run(ctx, recorder)
    except Exception:
        # finish() in the failure path too, so a crashed run still yields a
        # well-formed array ending in status "error".
        write_trace_safely(sink, recorder.finish("error"))
        raise

    tool_ctx.edits = list(result.edits)
    trace = recorder.finish("ok")
    write_trace_safely(sink, trace)
    published = publisher.publish(trace.trace_id, result, tool_ctx)
    return trace, published

Three details in that function are doing more work than they look like they are. The except block calls finish("error") before re-raising, so a crashed run still leaves a well-formed array rather than nothing. write_trace_safely swallows sink failures — a schema failure in the trace table must not take down the thing that fixes schema failures. And both defaults are rooted at ctx.project_root rather than the worker's current directory, which is not a mounted volume.

The demo

The seeded failure

The demo DAG carries a failure_mode parameter defaulting to "none", so the shipped behaviour is unchanged until you ask for a failure. Set it to schema_drift and extract() emits a record with a renamed field:

the drift
- return [{"id": 1, "customer_name": "example"}]  # emitted
+ class Event: id: int; name: str  # declared

The validation that catches it is derived from the contract, not hardcoded. Event.from_mapping reads the declared fields off the Event dataclass in events.py, the one type every sink accepts, so the runtime error and the eval's ground truth cannot drift apart. The exception names the missing field, the undeclared one that arrived instead, and the declared fields, because that message is the agent's primary evidence.

One failure, every configuration

Because drift is caught on the contract rather than against the DuckDB DDL, the same schema_drift mode fires with the Lakehouse Pattern on or off. When it is on, a generated test keeps the contract a subset of the table's columns.

Security boundary

The tool allowlist

Three tools. No bash, no write, no directory listing. The allowlist is not a convenience — it is the entire security model, because the agent runs inside an Airflow worker with access to a real repository.

ToolReturnsWhy it is a tool rather than prompt context
read_task_log Bounded log tail The trace records that the agent read it — evidence it diagnosed rather than pattern-matched the exception name.
read_repo_file File contents Path confinement is enforceable at a typed boundary. It is not, if the agent has a shell.
propose_patch Staged edit Produces a diff without touching the filesystem. The agent never writes.

Path confinement

The path argument is model output, so this is load-bearing rather than defensive. The order matters: resolve first — collapsing .. and following symlinks — then check containment.

src/<slug>/agentic/tools.py
def resolve(self, path: str) -> Path:
    root = self.project_root.resolve()
    candidate = (root / path).resolve()
    if not candidate.is_relative_to(root):
        raise ToolError(f"path '{path}' resolves outside the project root")
    return candidate

Three escape vectors are tested against real filesystem behaviour rather than string patterns: ../etc/passwd, an absolute /etc/passwd (which Python's / operator silently makes the whole path), and an actual symlink pointing outside the tree.

Staging, not applying

propose_patch uses str_replace semantics but records the edit rather than performing it. Both it and render_diff derive the file's post-edit content through one shared helper, _apply_staged_edits.

A bug this prevented

Originally propose_patch validated against the file on disk while render_diff applied edits sequentially in memory. Two views of the same state, kept in agreement by hand. A second edit overlapping text the first had rewritten was silently dropped from the patch while the metadata still claimed it. Collapsing both onto one derivation is the fix; the raised error is only the tripwire.

The seam

Where the non-determinism lives

AgentRunner is a protocol with one method. Three implementations satisfy it, and nothing downstream can tell which one ran.

ImplementationSource of truthNeeds a key
FakeRunnerA fixture you hand itNo
ReplayRunnerA recorded cassette, dispatched through the real toolsNo
ClaudeRunnerA live modelYes

ReplayRunner is the interesting one. It replays the model's decisions from a cassette but executes every tool call for real, so path confinement, edit staging and diff rendering are genuinely exercised. Its AgentResult is built from what dispatch actually staged, never from the cassette — an earlier version read a hand-authored edits field, which quietly demoted the whole tier to an elaborate mock.

Tier-dependent request parameters

The model is a cookiecutter variable, so request parameters cannot be interpolated blindly. temperature is valid on Haiku and returns HTTP 400 on Opus 5; output_config.effort is the reverse. A small table resolves this, and an unrecognised model gets the intersection valid everywhere — an empty dict.

src/<slug>/agentic/runner.py
_MODEL_PARAMS: dict[str, dict] = {
    "claude-haiku-4-5": {"temperature": 0},
    "claude-sonnet-5":  {"output_config": {"effort": "medium"}},
    "claude-opus-5":    {"output_config": {"effort": "medium"}},
}

def _model_kwargs(model: str) -> dict:
    # deepcopy, not dict(...): a shallow copy shares the nested
    # output_config with the module table, so one caller mutating it
    # would corrupt every later call.
    return copy.deepcopy(_MODEL_PARAMS.get(model, {}))
Observability

One JSON array per failure event

The entire run is captured as a single document whose top level is an array of elements in emission order. Because a healing run is single-threaded, emission order is causal order — which is why a flat seq replaces a parent/child span tree entirely.

0agent_runstatus running, carries the DAG correlation keys
1llm_turntoken counts from response.usage
2tool_callread_task_log — proves the log was actually read
3tool_callread_repo_file
4llm_turn
5tool_callpropose_patch
6resultthe structured diagnosis
7agent_runterminal element — ok or error, always present

The array being the unit of write makes atomicity structural rather than transactional: the document is written or it is not. It also makes assertions trivial — checking that the agent read the log before proposing a patch is a one-line comparison over a list.

Storage

One row per failure event when the Lakehouse Pattern is on; one file per event when it is off. Both persist structurally identical documents, so an eval asserting on a trace does not care which sink ran.

src/<slug>/agentic/create_traces_table.sql
CREATE TABLE IF NOT EXISTS agent_traces (
    trace_id    VARCHAR PRIMARY KEY,
    dag_id      VARCHAR,
    dag_run_id  VARCHAR,
    task_id     VARCHAR,
    try_number  INTEGER,
    occurred_at TIMESTAMP,
    status      VARCHAR,
    elements    JSON
);

DuckDB's native JSON support keeps aggregate queries first-class — unnest(json_extract(elements, '$[*]')) recovers a row-per-element view without the write path paying for that shape. The agent's own telemetry becomes just another dataset in the lakehouse, queryable with the same SQL as everything else.

Output

Publishing the patch

The default writes two files and requires no credentials: a unified diff ready for git apply, and a metadata document carrying the proposed title, body, confidence and edits. A generated scaffold that tried to push to a remote on first run would be a poor introduction, and most freshly generated projects have no remote at all.

GitHubPublisher ships alongside it and activates only when AGENTIC_GITHUB_REPO is set. It branches from the configured base rather than whatever HEAD happens to be, and restores the original branch on failure so a retry of the same trace is not blocked by a half-created branch.

A run with no edits is a real outcome

The agent may correctly conclude it cannot fix something. In that case there is no .patch file, but the metadata document is still written — that record is how a human learns the agent ran and gave up. The same guarantee holds when diff rendering fails: a render_error field distinguishes "could not render" from "chose not to edit", so the audit trail survives the case where it matters most.

Verification

Four tiers, two of which gate

TierMarkerRunnerGates CIProves
UnitnoneFakeRunner yes Plumbing: trace well-formed, patch renders, sinks agree
ReplaynoneReplayRunner yes The real loop: tool dispatch, confinement, diff rendering
LiveliveClaudeRunner no Agent quality against a live model
Gradedgraded+ ClaudeGrader no Scored, per-criterion feedback with written reports

uv run pytest runs the first two: fully deterministic, no key, no network. The other two are deselected by addopts and skip themselves when ANTHROPIC_API_KEY is unset — belt and braces, so someone who overrides the marker filter still does not get a surprise bill.

Cases are data

Each case is a YAML file declaring what to expect and which criteria gate. Adding a case means adding a file, not writing a test — which matters in a template, because a generated project's failure modes will differ from the ones shipped here.

evals/cases/schema_drift.yaml
expect:
  tools_called:
    must_call:    [read_task_log, read_repo_file, propose_patch]
    must_precede: [[read_task_log, propose_patch]]   # log before patch
  patch_targets: src/pkg/batch/dags/example_dag.py
score:
  required: [tools_called, patch_targets]   # these gate
  advisory: [diagnosis_mentions, min_confidence]   # these report

The required / advisory split is explicit in the data because the two kinds of criterion are genuinely different. patch_targets is objectively checkable, so it gates. diagnosis_mentions is keyword matching over prose: useful signal, poor gate. Encoding the distinction stops a later "fix" to a flaky eval from loosening the load-bearing half.

A criterion that could not fail

An earlier version asserted the exact tool sequence, including exactly two read_repo_file calls — a number copied from the cassette rather than derived from what the criterion means. A correct live model reading one file, or three, would have failed a gating criterion. Coverage plus ordering encodes the actual intent; the exact transcript survives as a replay-only check where it is meaningful.

The grader

The grader gets the same seam treatment as the runner — FakeGrader alongside ClaudeGrader — so a bug in the Markdown report table does not require an API key to catch. It receives the rubric, the trace array and the diff, but deliberately not the agent's system prompt: grading against the same instructions the agent was given measures compliance, not correctness. Its output is per-criterion rather than a single score, because one number tells you a regression happened while per-criterion feedback tells you which criterion moved.

Integration

Living inside a cookiecutter template

This is not an application — it is a Pattern in a template, and everything under {{cookiecutter.project_slug}}/ is Jinja-rendered before it is Python. Two constraints follow, and both are enforced by tests rather than convention.

The manifest invariant

hooks/post_gen_project.py holds a canonical PATTERNS list declaring, per flag, which files are deleted when it is off and which are gated — kept either way but containing their own Jinja conditional. A test reflects over the template tree and asserts the declared gated set exactly equals the files that actually reference that flag. It fails in both directions: declaring a file early is as loud as forgetting one.

The dependency nobody else has

The existing four Patterns are mutually independent. Agentic is the first with a cross-Pattern requirement — it heals a batch DAG, so without include_batch there is nothing to observe. The pre-generation hook rejects that combination with a clear message rather than generating a project that silently does nothing.

No dead branches

The template's central promise is that disabling a Pattern removes its files entirely. Two files were caught violating it during review — an unread grader cassette, and the traces DDL shipping when the Lakehouse Pattern was off and nothing could read it. Both are now removed with their flag, and a bake test greps for leftovers.

Portability

How coupled is this to one provider?

Structurally, very little. Concretely, in four places. Most of the runtime code — contracts, tracing, publishing, the healing orchestration, and every tool's actual behaviour — never names a provider at all.

Neutral todayStill coupled
contracts.py, tracing.py, publisher.py ClaudeRunner — expected; it is the implementation
Tool behaviour and ToolDefinition _MODEL_PARAMS — Claude model IDs
Replay cassettes — recorded in our own format Loop shapes: stop_reason, tool_use_id
The eval harness and scoring ClaudeGrader — the same coupling, duplicated

Tools are now declared provider-neutrally as ToolDefinition(name, description, parameters) with plain JSON Schema, and each runner renders them into its provider's shape — Anthropic nests the schema under input_schema, OpenAI under function.parameters. That rename was the one leak sitting on the wrong side of the seam.

A second provider is therefore a second implementation of the existing protocol, not a re-architecture. And because the cassettes record our format rather than provider wire format, a new runner inherits the entire deterministic eval suite unchanged.

Honesty

What is still open

These are known and deliberately unfixed rather than undiscovered. Recorded here because a walkthrough that only describes the parts that work is not a walkthrough.

GapConsequence
.gitignore rules for the other Patterns are still ungated The Agentic block is now gated, but dbt_packages/ and target/ still ship with dbt off, and logs/* with Batch off. data/ is the awkward one: Batch, Streaming and the evals fixtures all write there, so gating it needs a three-way condition and puts .gitignore in three more manifest entries. The most instructive bug of the build

The healing task originally read context["task_instance"] — its own TaskInstance, since it is an ordinary downstream task. The agent was told heal_on_failure had failed and was pointed at its own log. Every unit test passed, because they handed in a fake TaskInstance already carrying task_id="load": they asserted the mapping, not the source. Only a test that actually ran the DAG could catch it. The failed task's id is now passed explicitly from the wiring.
